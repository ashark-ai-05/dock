# Dock — Install, and the first sixty seconds

## Decision

Make Dock installable, and make the minute after installing it say what Dock is.

Two binaries reach a user's `PATH` — `dock` and `dockd` — and the six scripting
binaries fold into `dock <verb>`. The crate publishes as `dock-tui` with its binary
still named `dock`. Releases are generated by `dist`, cut from a tag, and reachable
through Homebrew, a shell installer, and `cargo install`. `dock doctor` proves an
install in one screen. A first-run card names four keys and gets out of the way.

## Problem

Dock cannot be installed by anybody.

`Cargo.toml` says `version = "0.1.0"`. There are no tags, no releases, and no
workflow that would make one. The README's quick start is `cargo run --bin dock`,
which asks a stranger to have a Rust toolchain and to clone a repository before they
can see anything. The repository is public and has zero stars.

The competition is not a features problem. herdr does one thing — a sidebar that rolls
agents up to blocked/working/done/idle — and Dock does that *and* the board, worktree
dispatch, handoffs with measured evidence, detection rules as editable data, hook-based
exact state, and a written safety invariant. herdr is nonetheless the one people have,
because it can be installed, and because Omarchy ships it: the Omarchy 3 manual binds
`Super + Ctrl + K` to a herdr keybindings viewer, next to the tmux one.

Every idea worth having about Dock is downstream of somebody being able to run it.

## Verified foundation

Read from the tree at `ead7408`, not assumed.

- **Eight binaries, none declared.** `Cargo.toml` has no `[[bin]]` section, so Cargo
  auto-discovers `main.rs` plus all seven files in `src/bin/`. `cargo install` would
  therefore put eight executables on a stranger's `PATH`, including `dock-programme`
  and `dock-inspect`, which are internal surfaces.
- **The scripting binaries are thin.** 825 lines total: `dock-agent` 83,
  `dock-dispatch` 118, `dock-handoff` 161, `dock-inspect` 74, `dock-programme` 180,
  `dock-workspace` 117, `dockd` 92. Each is a `main()` over the public library — see
  `src/bin/dock-inspect.rs:12`, which parses three flags and speaks the protocol.
- **The subcommand pattern already exists.** `main.rs:102-118` dispatches `detect`,
  `agent-state`, `hooks`, `handoff` and `task` on the first argument. Folding is
  extending a pattern, not inventing one.
- **`dock handoff` already exists twice, differently.** `main.rs:1691`
  (`handoff_command`) is agent-facing: a positional summary, `--question=`,
  `--check=name:pass`, and it reads git facts from the current worktree.
  `src/bin/dock-handoff.rs:68` is operator-facing:
  `--submit=PACKET.json | --inbox | --run-id=… --route=… --note=…`. Same word, two
  audiences. §1.2 resolves this.
- **What references the old names.** `scripts/smoke-slice5-macos.sh` (19),
  `smoke-slice4` (7), `smoke-slice3` (5), `smoke-slice6` (2), `README.md` (5), two
  older specs, and two files under `docs/`. The hits in `src/dispatch.rs` and
  `src/protocol.rs` are a doc comment, a run-id label at `dispatch.rs:6488`, and a test
  fixture string at `dispatch.rs:8617` — none is a process invocation.
- **Nothing has ever been released**, so there is no compatibility burden and no
  deprecation window to run. The fold can be clean and the old names can simply cease
  to exist.
- **`dock` is taken on crates.io** — registered 2022-06-06, one version, 1580 downloads
  all-time and 11 recent. Homebrew core has no `dock` formula, so a tap is unobstructed.
- **The GitHub description** is "The handoff desk for coding-agent runtimes", which is
  not the line the README leads with.
- **`dist` is alive**: v0.32.0, May 2026, with Linux cross-compilation through
  `cargo-zigbuild`.

## Scope

**In.** The binary fold; the crate rename; a `dist`-generated release pipeline over
four targets; a Homebrew tap; a shell installer; `dock doctor`; a first-run card; the
GitHub description.

**Out.** Themes and the config file, durable resurrection, racing agents, desktop
notifications, a website, and Windows. Windows is not deferred so much as excluded:
Dock is built on `forkpty`, Unix domain sockets, process groups and `SIGWINCH`, and a
Windows port is a second runtime rather than a fourth target.

## 1 · Two binaries

### 1.1 The shape

Each scripting binary becomes a module under `src/cli/`, exposing one entry point:

```rust
pub fn run(args: &[String]) -> Result<(), String>;
```

`main.rs` dispatches to them through the chain it already has at `main.rs:102`. The
files in `src/bin/` are deleted, and `Cargo.toml` gains explicit `[[bin]]` sections so
what ships is stated rather than discovered:

```toml
[package]
name = "dock-tui"

[[bin]]
name = "dock"
path = "src/main.rs"

[[bin]]
name = "dockd"
path = "src/bin/dockd.rs"
```

`dockd` stays a separate executable. A daemon wants to be exec'd directly by a
supervisor — launchd, systemd, a smoke script — and burying it behind
`dock daemon` would mean every supervisor config carries an argument whose only job is
to get back to where a second binary already is.

Bare `dock` still opens the dashboard. It is the product, it is what every existing
key sequence and every line of the README assumes, and a multiplexer that greets you
with `--help` has misunderstood what it is for.

### 1.2 Fork: what `handoff` means

`dock handoff` cannot mean both of the things it currently means.

**Chosen: `dock handoff` stays agent-facing; the operator half becomes `dock review`.**
The agent-facing form is the one the README teaches and the one an agent is told to
run, and it is the only one with a positional argument. The operator half — submit a
packet, list the inbox, record a decision — is the command-line face of the surface
`Ctrl+B i` already opens, and the dashboard already calls that surface *the review
queue*. Giving it the name the UI uses costs one rename in a repository nobody has
installed, and buys a verb that says which side of the desk you are standing on.

```
dock handoff "added a retry with backoff" --check="cargo test:pass"
dock review --inbox
dock review --submit=packet.json
dock review --run-id=dock_x --route=accept-scope --note="looks right"
```

*Declined: one verb whose flags are the union of both.* It parses — the agent form has
a positional and the operator form is flag-only — but it puts two audiences behind one
`--help`, and the first thing anybody reading it has to do is work out which half is
theirs.

*Declined: nesting, `dock handoff submit|inbox`.* A handoff summary is free text, so
`dock handoff inbox` is genuinely ambiguous between a subcommand and a one-word summary.

### 1.3 The verbs

| was | becomes |
|---|---|
| `dock-dispatch` | `dock dispatch` |
| `dock-inspect` | `dock inspect` |
| `dock-agent` | `dock agent` |
| `dock-workspace` | `dock workspace` |
| `dock-programme` | `dock programme` |
| `dock-handoff` | `dock review` |
| — | `dock doctor` (§3) |

`dock --help` lists every one of them with a line each, and each verb answers
`--help` for itself.

### 1.4 What has to follow

The five smoke scripts, the README's five references, `docs/terminal-runtime-parity.md`
and `docs/slice61-macos-walkthrough.md`. The two older specs are historical records of
decisions taken at the time and are **not** rewritten; a spec that is edited to match
later code stops being evidence of what was decided.

## 2 · Releases

`dist` is configured in `Cargo.toml` and generates the release workflow, the shell
installer and the Homebrew formula:

```toml
[workspace.metadata.dist]
cargo-dist-version = "0.32.0"
installers = ["shell", "homebrew"]
tap = "ashark-ai-05/homebrew-tap"
targets = [
  "aarch64-apple-darwin",
  "x86_64-apple-darwin",
  "x86_64-unknown-linux-musl",
  "aarch64-unknown-linux-musl",
]
```

Linux targets are **musl**, statically linked. The installer's whole promise is that a
downloaded binary runs, and a glibc build breaks that promise on precisely the machines
where a one-line install matters most — an older LTS, a container, Alpine. Dock links
no C library of its own beyond libc, so there is nothing to lose by it.

A `release-dry-run` job builds the full matrix on pull requests without publishing.
Cross-compilation breaks for reasons that have nothing to do with the change that
broke it, and finding that out at tag time means discovering it at the exact moment
the version number has already been spent.

Publishing to crates.io happens as `dock-tui`. `cargo install dock-tui` installs a
binary named `dock`, and keeping the crate on the registry is what lets
`cargo binstall dock-tui` resolve, since that reads crates.io metadata to find the
release artifacts.

## 3 · `dock doctor`

One screen that answers "is this install going to work", and every red line ends in
the command that fixes it.

```
$ dock doctor
 agents
   ✓ claude      hooks wired · resume verified
   ✓ codex       heuristic   · resume verified
   ✗ amp         heuristic   · no verified resume flag
   ─ 17 others   not installed
 daemon
   ✓ running · protocol v13 · /tmp/dock-501-…/dockd.sock
 clipboard
   ⚠ OSC 52 only, and TERM_PROGRAM=Apple_Terminal disables it
     → export DOCK_CLIPBOARD=helper
 install
   ✓ dock 0.1.0 at /opt/homebrew/bin/dock
```

Every line is a fact Dock can already establish: the agent roster comes from
`detect::AgentKind` and a `PATH` lookup, hook status from reading
`.claude/settings.json` the way `dock hooks` already does, resume from the same table
`Ctrl+B a` consults, the clipboard route from `DOCK_CLIPBOARD` and `TERM_PROGRAM`, and
the daemon from a `Hello`.

It exits non-zero if any line is `✗`, so it can be the last step of an install script
and the first step of a bug report. `⚠` does not fail: a clipboard route that cannot be
verified is not a broken install, and a doctor that cries wolf is a doctor people stop
running.

The probe and the verdict are separate: probing produces a plain struct, rendering and
exit code are functions of it. That is what makes the whole thing testable on a machine
where none of the twenty agents is installed.

## 4 · The first run

On the first launch with no state directory, one card over the first pane:

```
  ╭─ dock ────────────────────────────────────╮
  │  Ctrl+B ?   every key                     │
  │  Ctrl+B l   launch an agent               │
  │  Ctrl+B k   the task board                │
  │  Ctrl+B [   copy mode                     │
  │                                           │
  │  any key dismisses · never shown again    │
  ╰───────────────────────────────────────────╯
```

The pane is live behind it and any key dismisses it — including the key you meant to
press, which is then delivered. It is not a wizard, it does not have steps, and it
cannot be arrived at twice. Dismissal is recorded in the state directory beside the
layout.

This is the smallest thing that fixes the actual first-run failure, which is not that
Dock is hard to use but that nothing on an empty screen says the board and the agent
launcher exist at all.

## 5 · Positioning

The GitHub description becomes the README's own line — *"A terminal multiplexer that
understands coding agents"* — and the repository grows the topics somebody would
search: `tmux`, `terminal-multiplexer`, `tui`, `rust`, `ai-agents`, `claude-code`.
The homepage field stays empty until there is a page worth pointing at.

## Order of work

1. **The fold** (§1). Modules, `[[bin]]`, the `handoff`/`review` split, then the smoke
   scripts, README and docs. One commit per verb keeps the diff readable; the suite and
   the smoke scripts are the proof.
2. **The crate rename** (§2). `dock-tui`, binary still `dock`. Small, but it must land
   before anything is published under a name that cannot be changed afterwards.
3. **`dist`** (§2). Config, the dry-run job, the tap repository, then the first tag.
4. **`dock doctor`** (§3).
5. **The first-run card** (§4).
6. **Positioning** (§5).

Steps 4 and 5 do not depend on 1–3 and can move if something in the pipeline stalls.

## Testing

- The fold is covered by the existing suite plus the five smoke scripts, which drive
  the real binaries over a real socket. They are the reason this refactor is safe: they
  fail if a verb stops being reachable.
- `dock --help` lists every verb, asserted against the dispatch table rather than a
  literal, so a verb added without a help line fails.
- `doctor`'s renderer and exit code are tested over constructed probe results,
  including the all-red case, which no developer machine can produce.
- The first-run card: shown on an empty state directory, absent on a populated one, and
  the dismissing keystroke reaches the pane.
- CI gains the `release-dry-run` matrix, and a job that runs the built Linux artifact
  in a bare container to prove the static link.

## What done means

A person who has never seen Dock runs one command, gets a binary, runs `dock`, and is
told what to press. `dock doctor` tells them what is wired and what is not. None of it
requires a Rust toolchain, a clone, or the README.

## Out of scope, deliberately

- **A website.** The install one-liner can point at raw GitHub until there is a page
  worth the domain.
- **Signing and notarisation.** macOS Gatekeeper will quarantine a downloaded binary,
  and `brew` is the answer for now. Worth doing; not worth blocking a first release on.
- **Windows.** §Scope.
- **Themes, resurrection, racing, notifications.** Each is its own spec. This one is
  about being installable, which every one of them is downstream of.

## Risks

- **The fold touches the smoke scripts, which are macOS-only and slow.** A verb that is
  renamed but missed in `smoke-slice5-macos.sh` fails in CI rather than locally. Doing
  the scripts in the same commit as the verb they exercise keeps the blast radius to
  one verb.
- **musl and `forkpty`.** Dock's PTY handling goes through `nix`, which supports musl,
  but this has never been built for musl in this repository. The dry-run matrix exists
  to find that out before a tag, and the container job to find out whether the artifact
  actually runs.
- **`dist` owns the release workflow.** It generates `.github/workflows/release.yml`
  and regenerates it on upgrade, so local edits to that file are lost. Anything Dock
  needs at release time that `dist` does not offer belongs in a separate workflow.
