# Terminal-runtime parity matrix

Status reflects the shipped P0 real-terminal runtime, not complete terminal-emulator parity.
Every row below was checked directly against the code, not carried over from the original plan.

| Daily capability | Status | Current evidence / boundary |
|---|---|---|
| Multiple workspaces and panes | Shipped | Dynamic daemon-owned model and protocol v10 CLI; an older daemon must be stopped before this client can attach |
| Horizontal/vertical split | Shipped | Deterministic bounded binary layout tree |
| Focus, resize, rename, close | Shipped | Published keyboard-first map (`Ctrl+B` prefix) plus mouse equivalents; focus and geometry paint optimistically before strict socket authority replies |
| Zoom | Shipped | `Ctrl+B z` toggles a client-local full-area view of the focused pane; the daemon's layout tree is untouched, but the pane's inner geometry changes and the next frame announces the new PTY size |
| Layout persistence | Shipped | Owner-only atomic topology and labels |
| Bounded pane admission | Shipped | 64 panes per workspace; atomic refusal precedes receipt, pane, PTY, and process creation; explicit close reaps the owned runtime and frees the slot |
| Shell panes | Shipped | Every pane auto-launches `$SHELL` (falling back to `/bin/sh`) the moment it exists, bound under a synthetic `dock_sh_<workspace>_<pane>` run; a pane is never inert. An explicit launch into that pane displaces and retires the placeholder shell |
| Terminal input | Shipped | Full VT emulation via `vt100`, rendered through `tui-term`; agent TUIs and `vim` (including the alternate screen) work. Unprefixed keys reach the PTY; `Ctrl+B` is the command prefix, `Ctrl+B Ctrl+B` sends a literal `0x02`, and `Esc` is always forwarded, never intercepted |
| PTY resize | Shipped | Pane geometry drives `TIOCSWINSZ` plus `SIGWINCH` on the owned process group; `openpty` takes the initial size so a program never observes a placeholder size before its real one |
| Agent state detection | Shipped (heuristic tier, per-agent, whole-screen) | Classified from the agent's whole visible screen rather than a cursor-anchored tail. That distinction was a real defect for as long as detection existed: a full-screen agent leaves the cursor wherever it likes — a selection dialog puts it on the highlighted option and prints "enter to select … esc to cancel" *underneath* — so every pattern keyed on that chrome was matched against a haystack it could not be in, and an agent sitting on a chooser reported as idle. A chooser's chrome is matched rather than its numbered options, since agents print numbered lists in prose constantly. Twenty agents are recognised by binary name, and recognition is what puts one in the roster at all. Classification reads the terminal title ahead of the screen, because an agent sets its title to say what it is doing and that survives a screen which has scrolled the interesting part away — a rule can anchor on the first line when it means the title specifically. OSC 133 was considered for this and rejected: it marks *shell* command boundaries, so an agent started by typing its name sits at `133;C` for its entire lifetime including while it waits, and an agent launched as the pane's own process emits none at all. Three tiers, in order of trust, and the screen tier is now data rather than code: per-agent rules live in `~/.config/dock/agent-detection/<agent>.json`, replacing whichever of blocked/working/awaiting they name and inheriting the rest, so an agent that respells its prompts after a release is a file somebody edits rather than a version of Dock somebody waits for. JSON rather than TOML because these files are full of regexes and Dock already speaks JSON: TOML's two string forms escape backslashes differently, and a silently wrong pattern is the failure this exists to end. `dock detect <agent> [--explain]` prints the rules in force, where they came from, and — given a screen on stdin — which rule matched, which is the question that had no answer while this was compiled in. An agent that reports its own state through its event system wins outright — `dock hooks --install` wires Claude Code's `UserPromptSubmit`, `Stop`, `PermissionRequest`, `Notification` and `SessionEnd` to `dock agent-state`, so turn boundaries come from the agent rather than from a reading of its screen, and a report is sticky until the next one because a timeout would invent a transition nobody observed. Without hooks, working is decided by output rather than by text: a pane that wrote in the last 1.2 seconds is working, whatever this month's spinner is called. Three rounds of patterns tried to recognise working from the screen and were wrong each time, because every CLI spells it differently and respells it between releases. The screen is now asked one narrow question only — is this agent blocked on something it needs answered — which a pattern can answer reliably, since a permission prompt and a chooser paint fixed chrome. Blocked and done are deliberately different states: blocked is an agent that asked something and cannot continue — a permission prompt, a chooser — while done is one that finished its turn and will wait indefinitely. Collapsing the second into the first was tried and made every idle agent shout for attention until the roster meant nothing. Screen-content heuristic classifies each run as blocked/working/done/idle; the sidebar sorts blocked-first. Detection of external (non-Dock-launched) processes is no longer shown. It scanned the whole process table once at startup and never again, ignored the scope argument it was given, and so listed agents in Dock's own panes, in other terminals, and the user's own editor session — stale, unscoped, and unactionable, since Dock has no adoption path by design. The sidebar space it held now carries a clickable menu of what this dashboard can do. `discovery.rs` remains, unwired: the capability is worth keeping if it is ever scoped and refreshed properly |
| Signal delivery (`Ctrl+C`) | Shipped | The launch guardian `exec`s the worker instead of backgrounding it, so the worker keeps `SIG_DFL` for `SIGINT`/`SIGQUIT` — POSIX forces those to ignore for a non-interactive shell's async jobs, and `SIG_IGN` survives `exec`. `exec` preserves the pid, process group and session, so Dock's owned-group authority is unchanged. Every pane child is additionally handed `SIG_DFL` for `SIGHUP`, `SIGINT`, `SIGQUIT`, `SIGTERM`, `SIGTSTP`, `SIGTTIN` and `SIGTTOU` before `exec`, so how `dockd` itself was started (foreground, background job, `nohup`) cannot decide what a pane can be sent. Both delivery paths work: Dock's own `killpg(SIGINT)` and a `0x03` byte written to the PTY master. The guardian watcher, which no longer has a parent shell to retire it, exits on the `SIGHUP` the kernel raises when the session's controlling process dies |
| Client reconnect | Partial | A running dashboard holds two daemon connections — the event stream and a separate request connection, since `CLIENT_READ_TIMEOUT` is inert after `Subscribe` and makes a subscribed connection one-way. Only the event stream re-subscribes automatically on a dropped socket; the request connection has no reconnect path, so its loss ends the dashboard |
| Concurrent dashboards per daemon | Shipped (bounded) | The daemon admits 32 connections total; each running dashboard consumes 2 of them, so one daemon supports 16 concurrent dashboards. Slots release when a dashboard exits or its socket closes, so a crashed client recovers capacity on its own |
| Daemon restart | Intentionally different | Restart recovers layout metadata only, never processes: every durable pane returns as `restored` with no run binding; live-daemon fresh panes start with their auto-launched shell; old processes/output are never recovered |
| Safe exited-pane operations | Shipped | Metadata remains operable; stale PGIDs are never signalled |
| Owned PTY/process groups | Shipped | Only Dock-created groups; no adoption API. Retiring a group reads `killpg`'s EPERM as "the signal reached nobody", never as "something is alive": macOS keeps an unreaped zombie in its process group and answers EPERM for a group made only of them, so a successfully retired group is indistinguishable by signal from a live one. The EPERM path therefore consults the process table, which is the only witness that separates a group of zombies from one holding a live member Dock cannot signal — `sudo` inside a pane is the realistic case, and calling that group retired would strand a live descendant. An unreadable process table keeps the group. Linux never reaches this path, because a zombie there still accepts the group signal |
| Bounded live scrollback | Shipped | Per-pane configured row budget (`vt100::Parser`'s scrollback rows, default 2000 via `dockd --scrollback-rows`); oldest rows are discarded as live output arrives; absent from durable layout/restart recovery. The daemon announces this budget in every `pane_attached` frame and the client's replica is built with the same one, so the two sides retain the same amount of history rather than the client guessing at the default |
| Copy mode | Shipped, without a true freeze | `Ctrl+B [` (or a mouse drag) puts the focused pane into keyboard selection. It does **not** freeze the pane: `apply_event`/`PaneDelta` keeps feeding the parser, so on a pane that is still producing output the highlighted text scrolls out from under the selection. Deliberate scrolling no longer does that — the wheel and `k` past the top row move the selection's endpoints by however far the viewport actually went, so a selection keeps the characters it was placed on rather than silently re-aiming at whatever moved underneath, and an endpoint pushed off the screen ends the selection visibly instead of clamping to a row it does not mean. `hjkl`/arrows move, `g`/`G` jump to the top/bottom of what the client can currently see, `v` starts a selection, `y` yanks it. A bare `y` with no selection yanks the cursor's line instead, trimmed of trailing whitespace, and says so in the notice. `Esc` unwinds one level at a time — the search prompt first, then the mode itself — and `q` always leaves immediately. Visibly signalled by `COPY` in the pane's border and a footer that switches to the copy-mode bindings. Every key copy mode handles is swallowed before it reaches the pane, so a program running inside it (`vim`, an agent CLI, a shell reading raw input) never sees a mouse event or a copy-mode keystroke — Dock consumes both |
| Selection and clipboard | Shipped, with an inherent OSC 52 caveat | A drag inside a pane enters copy mode and extends a selection as the pointer moves, and **releasing it copies the selection** — the behaviour of iTerm2, Ghostty, WezTerm and GNOME Terminal, and what a user arriving from any of them expects. The highlight stays up after the release and `y` still yanks explicitly. A plain click (no drag) only focuses the pane and copies nothing, which is what keeps auto-copy from being destructive: a gesture that selected nothing can never overwrite a clipboard the user filled from somewhere else. Double-click selects the word under the pointer and triple-click the line, trimmed of trailing padding; `/`, `.`, `-`, `_`, `~`, `+`, `@` and `:` bind into a word, so `src/main.rs:12`, `user@host` and `localhost:8080` select whole (iTerm2's default set plus `@` and `:`; `,` and `;` are left out because in terminal output they end a list item far more often than they sit inside one). crossterm reports no click count, so it is derived from the previous press's time and cell — 450ms, same row, within one column. Middle- and right-click paste the last text *this dashboard* copied, through the same `encode_paste` the host's bracketed paste uses; the OS clipboard is deliberately not read, because reading it means `pbpaste` on the render thread, and per-application last-selection is also what a middle click means on X11 (PRIMARY). A copy writes OSC 52 (works over SSH, since it asks the *host* terminal to set its clipboard). `DOCK_CLIPBOARD` chooses the route — unset/`auto`/`osc52`, `helper` (`pbcopy`/`wl-copy`/`xclip`), `both`, `off` — and an unrecognised value is refused rather than silently leaving the user on the route they were trying to change. The helper path was previously unreachable code: `copy()` returned the first route that worked, and a write to a raw-mode alternate-screen stdout essentially never fails, so it always returned OSC 52 and a user on Terminal.app was told "copied" while their clipboard never changed. The helper is now spawned with its stdin dropped before anything waits on it (a tool reading to EOF never exits while the write end is open) and reaped on a detached thread, so a copy never blocks a frame on a subprocess; `xclip` is given `-selection clipboard`, without which it fills PRIMARY and Ctrl+V pastes nothing. OSC 52 remains one-way — the terminal never acknowledges receiving it, Terminal.app disables it outright, iTerm2 disables it by default, tmux ignores it without `set -g set-clipboard on` — and many terminals cap the payload (commonly around 100KB) and truncate past that silently. Dock therefore names what it *asked for* rather than claiming a clipboard it cannot check: the notice reads "OSC 52 (asked the terminal; it cannot acknowledge)". This is inherent to the protocol, not a defect to fix — there is nothing to acknowledge and wait for |
| Scrollback search | Shipped, viewport-scoped | `/` opens a search prompt over the pane's visible rows; `Enter` jumps to the first match and closes the prompt, `n`/`N` cycle forward/backward and wrap at both ends. `Esc` at the prompt cancels the prompt only; a second `Esc` leaves copy mode. Match columns are character offsets, not terminal cell widths: a row containing CJK ideographs or most emoji before a match reports a column short by the count of those wide characters (box-drawing characters are narrow in virtually every terminal font, so TUI borders never trigger this). Search scans the rows currently on screen rather than all of history, so scrolling back first (wheel, or `k` past the top row) widens what a search covers; it does not sweep the whole buffer in one pass |
| Scrollback navigation | Shipped | The wheel over a pane scrolls that pane's history and returning to the bottom resumes following live output; in copy mode `k`/`↑` past the top row walks back a row at a time, while `g`/`G` stay bound to the top and bottom of the current viewport. This works because `pane_delta` carries the raw bytes the pane's child wrote rather than a repaint of the result: the client's `vt100` parser scrolls on the same bytes the daemon's did and builds the same history. (A repaint is cursor-addressed and never scrolls, which is why the earlier `state_diff` stream left the client's scrollback permanently empty and the wheel a no-op.) History is per-connection and starts at the attach snapshot, as it does in tmux: a client that attaches mid-run cannot see what scrolled past before it arrived, a pane whose geometry changes is re-seeded and starts again, and nothing survives a daemon restart. There is a second re-seed trigger with the same effect: the daemon retains only `PANE_OUTPUT_LOG_BYTES` (1 MiB) of undelivered child output, so a burst larger than that between two 16 ms stream polls leaves the subscriber past the retained window, `OutputLog::since` returns `None`, and the client is re-seeded from a full snapshot — rebuilding its parser and dropping the history it had accumulated, with no notice beyond the scrollback going empty. This is the deliberate behaviour: the alternative is skipping bytes and rendering a corrupted grid. It needs an interactive program writing over a megabyte in a single frame (`cat` of a very large file, an unthrottled log firehose), so ordinary output never reaches it. Verified by driving the real binary under a PTY: after `seq 1 500`, twenty wheel-up notches moved the visible frame from lines 478–500 back to 418–441, and scrolling to the bottom followed new output again |
| Workspace navigation | Shipped | A tab strip names every workspace and numbers it by the digit that reaches it (`Ctrl+B 1`-`9`); `Ctrl+B w` filters them by name; `,`/`.` still step. Tabs and picker rows are clickable. All client-local: the daemon already sends every workspace's layout and has no notion of which one a client is looking at, so none of it costs a request or a protocol change. The strip appears only once there is more than one workspace, and costs those layouts one body row |
| File navigation | Shipped, viewport of one directory tree | `Ctrl+B f` lists files under the focused pane's own working directory, which shells report through OSC 7 as they `cd`, falling back to the bound repository root. Inside a repository the listing comes from `git ls-files --cached --others --exclude-standard`, so `.gitignore` is honoured; outside one it is a plain walk that skips `.git`, `target`, `node_modules`, `.venv`, `dist`, `build` and dotfiles by name, which is the closest approximation available without a gitignore parser. Capped at 5000 paths. Taking a row types the path into the pane with a trailing space rather than opening it: Dock cannot know which verb was wanted, and the path is what every verb needs. Listing runs synchronously on the UI thread, so a very large tree pauses the frame that opens the picker |
| Agent session resume | Shipped, per-adapter | `Ctrl+B a` relaunches the agent that last ran in the focused pane with its own continue-the-last-session arguments: `claude --continue`, `codex resume --last`, `amp threads continue --last`, each read from that CLI's own `--help` rather than assumed. The resumed agent is a Dock-launched process like any other, so the owned-process-group invariant is untouched — Dock still never adopts a process it did not start. What persists is the agent's own transcript, which it files under the working directory and finds again itself, so a resume survives the pane's process dying, a daemon restart, and a reboot, none of which adopting a live process could. Two limits follow from resuming *the most recent session for a directory*: two panes running the same agent in the same directory share that most-recent, so resuming one can land on the other's session; and an agent whose flags Dock has not verified (GitHub Copilot CLI) reports that it cannot be resumed rather than launching without the flag, which would look like a resume and silently discard the conversation. A repository-bound run resumes into the same task and worktree; an unbound run resumes in its own directory, which is what protocol v9 added arguments to `TerminalLaunchRequest` for |
| Agent review loop | Shipped, with history | `Ctrl+B i` shows every handoff and the decision it has already had, undecided first: what an agent produced is asked long after the queue is drained, and a queue that forgets is no record at all. Read from the daemon's own store rather than over the socket — the pending queue has a request and the answered ones do not, and this client computed that directory itself and handed it to the daemon at startup, so a second protocol version would buy nothing. It holds the handoffs agents submitted through `dock-handoff --submit` and are waiting on a human for. The daemon side — `SubmitHandoff`, `ReviewInbox`, `Decide`, and the `HandoffPacket`/`HandoffRecord`/`ReviewDecision` types — already existed and was already tested; what was missing was any way to see or answer the queue from the dashboard, so a submitted handoff went somewhere nothing on screen ever showed. Each entry renders the agent's own summary and question beside the evidence the daemon measured (changed files, insertions, deletions, branch), so a claim is never read without what was actually observed. `a` accepts scope and `c` requests changes; both require a note, collected before anything is sent because `ReviewDecision::new` refuses an empty one. `Esc` unwinds one level at a time — the note first, then the queue. The recorded decision sets `external_task_completed: false` and `git_mutated: false` and the overlay says so on screen: Dock records a decision and never merges, touches Git, or closes the external task |
| Task board | Shipped, repository-optional, column view | `Ctrl+B k` draws a column per status with cards inside them, which is the point of a board: the shape says where work has piled up, what is in flight and what waits on a person, none of which a list sorted by status shows at a glance. `←`/`→` moves between columns, `↑`/`↓` between cards, `<`/`>` moves the card itself, `n` starts a task and `Enter` puts an agent on one. Cursor movement lives in `BoardView`, apart from the drawing, so the awkward cases — an empty column, a column that empties when its last card leaves, the edges — are decided by something testable without a terminal. The overlay is sized to its tallest column rather than the screen, and leaves the dashboard's own footer room, since that footer is painted after every overlay and would otherwise write over the bottom of this one. It reads the tasks in `<repository>/kanban/tasks/*.md`, parsed straight from their YAML front matter rather than through `kanban-md`, so the board renders on a machine where that binary is not installed — which is most of them. Only unindented keys between the `---` fences are read, so the `tags` and `depends_on` list items cannot be mistaken for fields. Tasks sort by where the work is (in-progress, review, backlog, todo, done) and a status Dock does not know sorts last rather than vanishing. One malformed file is skipped, never the board. Moving a task between statuses still needs `kanban-md`; reading never does. A dashboard outside a repository reads a personal board at `~/.dock/board/tasks` instead, so there is always somewhere to track work — the original board was repository-only and simply had nothing to show. `Ctrl+N` in the chooser turns the typed query into a task, and only on that personal board: a repository's belongs to `kanban-md` and to whoever commits to it, so Dock refuses there and says why. New ids continue past the highest present rather than filling gaps, since a gap usually means a task was archived rather than deleted |
| Task dispatch and worktrees | Shipped | Taking a task from the board runs `git worktree add` on a `dock/task-<id>` branch beside the repository, then launches the last-used agent bound to that worktree and task. This is the only mutation Dock performs inside a repository, and the README's safety invariant was amended to say so precisely rather than left claiming Dock never creates worktrees. It is idempotent — a branch that already has a worktree is reused, so dispatching a task twice lands in the first one — and refuses an occupied path rather than writing into it. The client creates the worktree and the daemon still validates that a supplied worktree is a Git worktree top-level inside the repository before binding a run to it, so Dock did not gain the power to dispatch into an arbitrary directory by gaining the power to make a worktree. Dock never removes a worktree or branch, including its own: it cannot know what is still wanted |
| Git surface | Shipped, diff-only | `Ctrl+B g` shows the focused pane's worktree — branch, changed files, insertions, deletions, uncommitted entries, and the diff against `HEAD` — painted with Dock's own semantic tokens rather than piped through `delta`, which would only bury ANSI in text the overlay then has to un-escape to style again. A pane dispatched onto a task therefore shows that task's worktree, not the directory the dashboard started in. `j`/`k` scroll, `g`/`G` jump to either end, and scrolling saturates rather than paging past the last line into a blank overlay. Read-only: it stages, commits, and reverts nothing, so it is a window onto Git rather than a replacement for `lazygit` |\n| Which-key bar | Shipped | While `Ctrl+B` is held the footer publishes the whole binding table. With the bindings added for workspaces, files, resume, review, board and Git it no longer fits two rows, so it now grows over the bottom of the body while the prefix is held and gives those rows back on release. The alternative was shaving words off the table until the last entry fitted, which truncates silently and reads as a missing binding |\n| Event-stream cost | Shipped | The stream polls every 16ms and asked `inspect` for a full picture each time, which took a fresh `ps -axo` snapshot and then parsed that snapshot once per pane. On an ordinary machine `ps` costs about 39ms for 839 processes, so each poll ran ~55ms rather than 16ms and the stream updated at roughly 18Hz instead of 62Hz — the daemon was not saturating a core, it was simply too slow to keep its own schedule. The table is now shared for 500ms and identified by a generation, and each run's agent identity and state are memoised against `(generation, output epoch, output length)` — every input that can change the answer. A pane that has written nothing since the last poll and is looking at the same table costs one hash lookup instead of a 79KB parse and a full-screen scan. Measured on the same four-pane scenario with one subscriber: 1.71s of CPU per ten seconds before, 0.27s after |
| Pane swap | Deferred | Follow-on tree operation |
| Themes/configuration | Partial | Warm terminal-modern theme shipped, with rounded borders and semantic colour tokens for every agent state; loading alternative palettes as data is deferred |
| Notifications | Deferred | Follow-on |
| Mouse layout interaction | Shipped, near-complete | Pane focus, divider resize, dismiss, and fixed-profile launch mirror keyboard-accessible actions. Dismissing all discovered external agents (`d` in the sidebar) is mouse-only — there is no keyboard binding for it, distinct from the `Ctrl+B d` "leave" command. The tab strip carries `✎` on the active tab (rename the workspace, which is the only path to a workspace rename: `Ctrl+B r` has always renamed the focused pane) and a trailing `+` (new workspace). The focused pane carries `⇋ ⇵ ×` on its **lower** border — split, split, close. Lower rather than upper because the top border already carries the pane's identity and, on an exited pane, the key that restarts it; the first attempt put them on top and truncated that hint to "Ctrl+B R resta ×". An exited pane offers close alone, since splitting a dead pane is meaningless and its hint is worth the room. Closing the last pane of a workspace removes the workspace, so closing a workspace needs no separate control |

Durable layout records contain no raw terminal content, command vectors, PIDs, process-group IDs, retained run bindings after restart, or absolute repository/worktree paths. Git, task, worktree, and programme authority remains unchanged.
